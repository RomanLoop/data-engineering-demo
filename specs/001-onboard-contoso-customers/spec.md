# Pipeline Specification: Onboard Contoso Customers

**Branch**: `001-onboard-contoso-customers`

**Created**: 2026-09-07

**Status**: Draft

**Input**: User description: "Onboard Contoso 1M customers entity end-to-end: Meltano CSV-Ingestion, bronze dedup, silver cleansing, gold, serving"

## Overview

Onboard the `customers` entity from the Contoso 1M dataset end-to-end — landing zone (Stage-1: native Spark bulk load via OneLake; long-term: Meltano CSV extraction, see Source & Ingestion), bronze append/dedup, silver cleansing + SCD2 historization, gold business logic, and a serving view. This is the **first** dataset onboarded into the repo, so it doubles as the reference pattern: subsequent entities (more Contoso tables, then other sources) are expected to follow the same shape.

## Source & Ingestion

- **Source system**: [SQLBI Contoso-Data-Generator-V2-Data](https://github.com/sql-bi/Contoso-Data-Generator-V2-Data/releases) — ready-to-use release asset `csv-1m.7z` (MIT-licensed, synthetic/fake data, no real-PII risk). **Resolved 2026-09-07**.
- **Extraction method**: Meltano `tap-csv` is the target long-term method, but is currently **blocked**: the only available Meltano→Azure-Blob target (`target-azureblobstorage`) authenticates via storage account key, while Fabric OneLake only accepts Azure AD (service principal) auth — no compatible Meltano target exists yet. **Stage-1 stopgap** (temporary, tracked exception — see plan.md Constitution Check): `customer.csv` is uploaded to the lakehouse's OneLake Files area (`scripts/upload_to_onelake.py`) and bulk-loaded as a Delta table by a native Spark job (`dbt run-operation bootstrap_landing_customer`) standing in for the landing zone — `dbt seed` was tried first and measured 30+ minutes for 105K rows before killing its own Livy session, so it was rejected — until the Meltano→Fabric path (Azure Storage Account + Fabric OneLake Shortcut, or an AAD-capable target) is implemented.
- **Load pattern**: one-time initial full load, then repeated delta loads via the delta-load simulator (new customers + updates to existing customers), per AGENT.md §4.
- **Expected volume & frequency**: 104,990 customer rows (confirmed by downloading and inspecting `customer.csv` from the archive during Phase 0 research — the "1M" in the release name refers to the `sales`/`orderrows` tables' scale, not row count per table). Delta loads run on-demand via the simulator, not yet on a fixed schedule (Dagster not yet integrated, per AGENT.md §10).
- **Landing format**: CSV, UTF-8, overwritten on every load (landing is a pure landing zone, no history kept there — see AGENT.md §5).

## Entities & Data Contract

### Entity 1 - customers (Priority: P1)

**Business key**: `CustomerKey` (per the SQLBI Contoso V2 customer dimension; source column name kept as-is, renamed to snake_case `customer_key` in silver per the dbt style guide).

**Why this priority**: Only entity in scope for this spec — establishes the reference pipeline pattern before any other entity is onboarded.

**Grain**: One row per customer. Confirmed via Phase 0 research: `CustomerKey` is unique across all 104,990 rows with zero nulls — the source file is a flat current-state snapshot, not a change-history export. `StartDT`/`EndDT` are per-customer attribute fields generated by the tool (not multiple rows per customer), so they are **not** a substitute for our own SCD2 versioning.

**Key columns** (confirmed against the downloaded CSV in plan.md Phase 0 research): `CustomerKey`, `GeoAreaKey`, `StartDT`, `EndDT`, `Continent`, `Gender`, `Title`, `GivenName`, `MiddleInitial`, `Surname`, `StreetAddress`, `City`, `State`, `StateFull`, `ZipCode`, `Country`, `CountryFull`, `Birthday`, `Age`, `Occupation`, `Company`, `Vehicle`, `Latitude`, `Longitude`.

**PII columns**: `GivenName`, `MiddleInitial`, `Surname`, `StreetAddress`, `City`, `ZipCode`, `Birthday`, `Company` — treated as PII by default per AGENT.md §6 (maskable in non-prod via `mask_pii_columns`). Data is synthetic/fake (SQLBI generator output), so this is a contract-hygiene default for the pipeline pattern, not a real-world privacy risk for this particular dataset.

**Independent test**: Can be extracted, built through bronze → silver → gold → serving, and validated independently of any other entity by running the initial load and querying `serving_customers` for a known sample of records.

**Acceptance scenarios**:

1. **Given** a fresh initial load of the customers CSV, **When** the pipeline runs (landing → bronze → silver-cleansed → silver-historized → gold → serving), **Then** `serving_customers` contains one row per source customer record, with zero duplicate business keys in bronze.
2. **Given** a delta load simulating N new customers and M updates to existing customers, **When** the pipeline reruns, **Then** bronze gains exactly N new rows (existing M updated records produce new bronze rows only if their dedup columns changed) and `silver_contoso__customers` reflects the M updates as new SCD2-versioned rows.

## Layer Placement & Transformations

- **Bronze** (`bronze_contoso__customers`): append-only insert of new/changed customer records; dedup-before-insert on business key + dedup columns (macro `dedup_before_insert`); `_ingested_at` technical column; `full-refresh` forbidden.
- **Silver**, two models (cleansing separated from historization — see plan.md for the materialization rationale):
  - `silver_contoso__customers_cleansed` (view): type casting (e.g. dates, numeric fields), renaming to snake_case per the dbt style guide, enrichment only from existing bronze columns (no joins to other models).
  - `silver_contoso__customers` (incremental/merge): applies SCD2 versioning on top of the cleansed view. Customers is classic master data, so **all** non-key columns are `meta.scd2_columns` — no SCD1 columns for this entity (every attribute change gets a new versioned row with `_valid_from`/`_valid_to`/`_is_current`).
- **Gold** (`gold_customers`): business logic on top of silver customers only (no other entities exist yet to join against); business keys passed through, no surrogate keys.
- **Serving** (`serving_customers`): a consumable view over gold; no row-level security required yet (see Assumptions — no consumer roles defined in Stage 1's single-workspace setup).

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: The pipeline MUST land the Contoso customers CSV into the landing zone, overwriting it on every run. **Stage-1 stopgap**: via a native Spark bulk load (`dbt run-operation bootstrap_landing_customer`, reading `data/contoso/customer.csv` after it's uploaded to OneLake Files) standing in for the landing zone, since Meltano→Fabric ingestion is currently blocked (see Source & Ingestion). The long-term implementation MUST be Meltano `tap-csv`, once a Fabric-compatible target/loader path exists.
- **FR-002**: The bronze model MUST append a customer record only when its business key + configured dedup columns are not already present in bronze (idempotent, dedup-before-insert), and MUST NOT support `full-refresh`.
- **FR-003**: The bronze model MUST enforce a dbt contract (`contract: {enforced: true}`) with `meta.business_key`, `meta.dedup_columns`, and `meta.pii_columns` populated, plus a `_ingested_at` technical column.
- **FR-004**: The `silver_contoso__customers_cleansed` model MUST cast column types and rename columns to snake_case per the dbt style guide, and MUST NOT join to any other model — enrichment is limited to the same table's columns and lookups.
- **FR-005**: The silver historization model (`silver_contoso__customers`) MUST enforce a dbt contract with `meta.business_key` and `meta.scd2_columns` populated (all non-key columns — customers is master data, no SCD1 columns for this entity), applying SCD2 (versioned history: `_valid_from`/`_valid_to`/`_is_current`) on any change. The upstream cleansing model (`silver_contoso__customers_cleansed`) MUST also enforce a contract with `meta.business_key` populated.
- **FR-006**: The gold model MUST expose customers using the business key only (no surrogate key added), applying any customer-level business logic required by downstream consumers.
- **FR-007**: The serving layer MUST expose a `serving_customers` view built on the gold model.
- **FR-008**: New columns appearing in the source CSV MUST be appended automatically (`on_schema_change: append_new_columns`) without breaking `serving_customers` for existing consumers.

### Data Quality & Non-Functional Requirements

- **NFR-001**: Reruns MUST be idempotent — rerunning the initial load twice produces identical row counts in bronze, silver, gold, and serving.
- **NFR-002**: PII columns (per `meta.pii_columns`) MUST be maskable via `mask_pii_columns` in non-prod; currently a no-op in Stage 1 (single prod-only workspace, see AGENT.md §8), but the macro must already be exercised/tested against this entity.
- **NFR-003**: The delta-load simulator MUST be able to generate both new customer records and updates to existing customer records for this entity, to validate FR-002 and FR-005.

### Edge Cases

- A record with a known business key arrives with a **different** value in a tracked (dedup/SCD2) column → treated as a genuine update: new row in bronze (dedup columns changed), and `silver_contoso__customers` versions it as a new SCD2 row (prior version's `_valid_to` closed out).
- The source introduces a **new column** → appended automatically in bronze/silver per additive schema evolution (FR-008); does not fail existing consumers.
- The source **removes or renames** a column → out of scope for this spec; handled as a deliberate, separate change per AGENT.md §3 principle III, not automatically.
- **Duplicate business keys within the same load batch** → only the first occurrence per business key is inserted into bronze in a given run; duplicates within a batch are dropped, not silently averaged/merged.
- **Null or malformed business key** → the run MUST fail loudly for that record rather than silently dropping or guessing (default per AGENT.md agentic conventions); malformed records are surfaced for inspection rather than landed silently.

## Success Criteria *(mandatory)*

- **SC-001**: Initial load lands 100% of source customer rows in bronze with zero duplicate (business key + dedup columns) combinations.
- **SC-002**: Rerunning the initial load twice produces identical row counts in bronze, silver, gold, and `serving_customers` (idempotency proof).
- **SC-003**: A delta-load simulator run with N new + M updated customer records results in exactly N new bronze rows and M correctly SCD2-versioned rows in `silver_contoso__customers`.
- **SC-004**: All contracted columns on `bronze_contoso__customers`, `silver_contoso__customers_cleansed`, `silver_contoso__customers`, and `gold_customers` pass their dbt tests and contract resolution with zero failures.
- **SC-005**: `serving_customers` resolves and returns the expected row count end-to-end, proving the full bronze→serving slice works.

## Assumptions

- **Meltano→Fabric ingestion is temporarily blocked** (2026-09-07): `target-azureblobstorage` (the available Meltano Azure Blob target) only supports storage-account-key auth; Fabric OneLake only accepts Azure AD auth. Stage 1 uses a native Spark bulk load via OneLake as a stopgap standing in for the landing zone (see FR-001) — `dbt seed` was tried first (2026-09-09) and rejected after measuring 30+ minutes for 105K rows, then a killed Livy session. This is a tracked, temporary exception to AGENT.md §4/constitution's "Meltano-only" rule — not a permanent architecture change. Follow-up work (tracked separately, not in this spec's tasks.md): stand up an Azure Storage Account as the Meltano target and a Fabric OneLake Shortcut onto it (recommended path), or an AAD-capable target, then remove the bulk-load bootstrap.
- No delta/change-data-capture sample exists upstream for this source (the release's "delta-1m" asset turned out to be Delta Lake/Parquet table *format*, unrelated to change data) — our own delta-load simulator must synthesize new/updated customer records itself (e.g. by sampling/perturbing the static snapshot), not replay a vendor-provided change feed.
- No row-level security is required yet for `serving_customers` — Stage 1 runs a single workspace/prod environment with no defined consumer roles (AGENT.md §8/§11).
- This spec covers only the `customers` entity. Other Contoso entities (e.g. products, orders, stores) are separate future specs, onboarded the same way once this reference pattern is validated end-to-end.
- This is the first entity onboarded, so the shared macros (`dedup_before_insert`, `mask_pii_columns`, `apply_scd1`, `apply_scd2`) are created here rather than merely reused.
- Data is synthetic (generator output), so no real customer PII is ever actually at risk here — PII tagging is still applied properly since the whole point of this entity is to establish the correct contract pattern for real future sources.
