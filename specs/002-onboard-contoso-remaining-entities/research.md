## Decision 2: `apply_scd1` real implementation (first use — was a docstring-only stub)

- **Decision**: Implement SCD1 (`orders`, `orderrows`) using dbt-fabricspark's native `incremental_strategy='merge'` (confirmed supported for `file_format: delta`, which every Fabric lakehouse table is, by reading `dbt/include/fabricspark/macros/materializations/models/incremental/validate.sql` in the installed adapter), with `unique_key` set to the business key (list — `merge` supports composite `unique_key` natively) and `merge_update_columns` set to `apply_scd1_update_columns()`'s return value (unchanged from the existing stub).
- **`_loaded_at`/`_updated_at` mechanics**: the model's own SELECT (not the merge machinery) computes both columns via a `LEFT JOIN` against `{{ this }}` on the business key:
  - `_loaded_at` = `coalesce(_existing._loaded_at, current_run_timestamp())` — preserves the original first-seen timestamp across every subsequent merge.
  - `_scd1_hash` = `generate_hash(scd1_columns)` (new value, computed from the incoming row).
  - `_updated_at` = `case when _existing._scd1_hash is null or _existing._scd1_hash != <new hash> then current_run_timestamp() else _existing._updated_at end` — only bumps when something in `scd1_columns` actually changed, per the macro's existing docstring contract; a rerun with no real change leaves `_updated_at` untouched even though the MERGE still runs (idempotent by value, not just by row-count).
  - This mirrors `dedup_before_insert`'s hash-comparison approach (reuses `generate_hash`) rather than inventing a second change-detection mechanism.
- **Why native `merge` over a hand-rolled MERGE (as SCD2 uses a hand-rolled pre_hook UPDATE)**: SCD2 needed a hand-rolled `expire_scd2_current_rows` because dbt's native incremental strategies have no "insert a new version and expire the old one" concept — that's inherently a two-statement operation dbt doesn't model. SCD1 is exactly what `merge` already means ("upsert by key"), so there's no reason to bypass it; doing so was the actual root cause of both SCD2 bugs found during `001` (working around dbt's model instead of using it). Using the native strategy here is the simpler-alternative-not-rejected case.
- **Composite key note**: `orderrows`' `unique_key: [order_key, line_number]` — the `merge` strategy's `unique_key` accepts a list natively (unlike `apply_scd2`'s hand-rolled `expire_scd2_current_rows`, which only supports a single-column business key — see Decision 5 below, not exercised by this spec but recorded as a known limitation).

## Decision 3: SCD1 correctness test (new)

- **Decision**: Add `assert_silver_contoso_orders_orderrows_no_duplicate_current.sql` — a singular test asserting zero rows where `count(*) > 1` grouped by business key, run against both `silver_contoso__orders` and `silver_contoso__orderrows` (via a `union all` of the two group-by checks, or two separate tests — decided at implementation time based on which reads more clearly). This is the SCD1 equivalent of the SCD2 gap/overlap tests: proves the merge is genuinely overwriting in place, not accumulating duplicate rows per key the way a bug in `unique_key`/`merge_update_columns` configuration would silently allow (e.g. falling back to `append` if `unique_key` were misconfigured).
- **Alternatives considered**: Relying solely on the contract's `unique` test on the business key — rejected as insufficient on its own only in the sense that it duplicates the same assertion; kept the contract-level `unique` test too since it's the standard, expected place a data consumer would look, and the singular test as a stronger delta-load-specific regression guard (mirrors why `001` kept both dbt's built-in tests and the two custom SCD2 singular tests).

## Decision 4: Generalize the existing SCD2 gap/overlap tests to `product`/`store`

- **Decision**: The two singular tests from `001` (`assert_silver_contoso_customers_no_overlapping_validity.sql`, `assert_silver_contoso_customers_no_gaps_in_validity.sql`) are hardcoded to `ref('silver_contoso__customers')`. Generalize them to run against any SCD2 model by looping over a fixed list of SCD2 model names (`['silver_contoso__customers', 'silver_contoso__product', 'silver_contoso__store']`) inside the test SQL (`union all` across a Jinja `{% for %}` loop), rather than hand-writing 3×2 = 6 near-identical test files.
- **Rationale**: Same "don't duplicate near-identical files six times" reasoning as Decision 5/plan.md's landing-bootstrap generalization. The list of SCD2 models is small and changes rarely enough that a hardcoded Jinja list is simpler than inventing a dbt-tags-based or `graph.nodes`-based auto-discovery mechanism for it.
- **Alternatives considered**: Auto-discovering SCD2 models via `graph.nodes.values() | selectattr('meta.scd2_columns', 'defined')` — more "clever," rejected as unnecessary indirection for 3 models; revisit if a dozen+ SCD2 entities exist someday.

## Decision 5: Generalized landing bootstrap macro

- **Decision**: `bootstrap_landing_table(entity, csv_path, columns)` — one macro, called once per entity via `dbt run-operation bootstrap_landing_table --args '{entity: product, csv_path: Files/contoso/product.csv, columns: [{name: ProductKey, type: int}, {name: ProductCode}, ...]}'` (an ordered list of `{name[, type]}`; a column with no `type` passes through as the CSV's inferred string type). Builds `landing.landing_<entity>` as `CREATE OR REPLACE TABLE ... USING DELTA AS SELECT <explicit column list, casting where a type is given> FROM <temp view over the CSV>`, same idempotent pattern as `001`.
  - **Revised during live validation (2026-09-09, T018)**: originally designed around Spark SQL's `SELECT * REPLACE (...)` (a partial `column_casts` dict, no need to enumerate every column) — this is **not supported on this Fabric Spark runtime** (`[PARSE_SYNTAX_ERROR] Syntax error at or near '('` on the first live `bootstrap_landing_table` call). Fell back to full column enumeration, matching `bootstrap_landing_customer`'s original style, exactly as the macro's own pre-written fallback note anticipated. The `columns` list is more verbose per call than `column_casts` would have been, but is what actually works against this runtime.
- **Per-entity column casts** (confirmed against the real headers in Decision 1):
  - `product`: `ProductKey int, Weight double, Cost double, Price double, CategoryKey int, SubCategoryKey int`
  - `store`: `StoreKey int, GeoAreaKey int, OpenDate date, CloseDate date, SquareMeters double`
  - `date`: `Date date, DateKey int, Year int, YearQuarterNumber int, Quarter int, YearMonthNumber int, MonthNumber int, DayofWeekNumber int, WorkingDay int, WorkingDayNumber int`
  - `currencyexchange`: `Date date, Exchange double`
  - `orders`: `OrderKey int, CustomerKey int, StoreKey int, OrderDate date, DeliveryDate date`
  - `orderrows`: `OrderKey int, LineNumber int, ProductKey int, Quantity int, UnitPrice double, NetPrice double, UnitCost double`
- **`bootstrap_landing_customer` intentionally left untouched**: already shipped, tested, and live-validated in `001`; retrofitting it onto the new generic macro is a pure refactor with no functional benefit for this change and a real regression risk against a working, validated pipeline. Tracked as optional cleanup, not required by this spec.
- **Alternatives considered**: Six separate `bootstrap_landing_<entity>` macros, one per entity, exactly mirroring `001`'s style — rejected in plan.md's Structure Decision (six near-duplicate 70-line macros vs. one parameterized macro + a small per-entity args literal).

## Decision 6: `apply_scd2`'s single-column business-key limitation (known, not fixed here)

- **Finding**: `expire_scd2_current_rows` (in `apply_scd2.sql`) hardcodes `business_key_col = business_key[0]` — it only ever joins/predicates on the *first* business-key column, silently ignoring the rest of a composite key.
- **Decision**: **Not fixed in this change.** Neither SCD2 entity onboarded here (`product`, `store`) has a composite business key — both are single-column (`ProductKey`, `StoreKey`), so the limitation isn't exercised and doesn't need to be proven correct now. Fixing it speculatively, without a real composite-key SCD2 entity to validate against, risks the same class of silent bug `001` already hit twice (see `apply_scd2.sql`'s own bug-history docstring) — this project's own precedent is to fix macro bugs only against a real, live-validated case.
- **Follow-up**: recorded here so it isn't rediscovered the hard way — if a future entity needs SCD2 over a composite key, `expire_scd2_current_rows` needs its join predicates extended from a single `business_key_col` equality to an AND-chain (or a `concat_ws`-based composite comparison, consistent with how `generate_hash` already handles composite key lists) before that entity's delta-load validation.

## Decision 7: Extended delta-load simulator, per-entity scripts vs. one generic script

- **Decision**: One simulator script per entity (`scripts/simulate_delta_load/contoso_<entity>.py`), mirroring the existing `contoso_customers.py` structure (new-record sampling + existing-record perturbation, `--new`/`--updated`/`--seed` CLI args), not one generic simulator parameterized by schema.
- **Rationale**: Unlike the landing bootstrap (pure mechanical CSV→Delta load, genuinely identical shape per entity), each entity's "what does a realistic update look like" logic differs meaningfully (e.g. perturbing `orders.DeliveryDate` vs. `store.CloseDate` vs. `product.Price` are different domains with different realistic mutation rules) — genericizing this would mostly just move the per-entity logic into a config blob instead of a Python function, without reducing real complexity. `001`'s own script is already the template to copy per entity.
- **Alternatives considered**: One generic script with a per-entity YAML/JSON mutation-rules config — rejected as premature abstraction for 6 entities; revisit if a much larger number of entities need this later.

## Decision 8: SCD2 `expire_scd2_current_rows` redesign — pre_hook → post_hook (found live, T020)

- **Finding**: `product`'s first real delta-load validation (T020) reproduced a duplicate-`_is_current` bug on the surface identical to `001`'s T022 "Bug 1" — but `001`'s fix (call `is_incremental()` only after `config(materialized=...)`) was already correctly in place in `silver_contoso__product.sql`, mirrored verbatim from `silver_contoso__customers.sql`, and the bug still happened. Deeper investigation (bisecting via `dbt compile`/manifest inspection, matching this project's established debugging style) found the true root cause: **dbt's config-extraction pass re-executes the entire model template in a stub context** (no live adapter, no real `model.meta`, un-overridden schema resolution) purely to discover `config()` calls — and whatever a `config()` argument evaluates to *in that stub pass* is what gets used, never re-evaluated against the real compile pass's context, even though the call site is textually inside the body that *does* get properly re-rendered later for everything else. This is the same *class* of gotcha as the `model.meta`-Undefined-during-static-parse issue found in `001` (a preliminary pass without full context silently diverges from the real one) but hits `is_incremental()`, `load_relation()`, and `{{ this }}`'s schema resolution too — and specifically poisons anything feeding a `config()` argument, regardless of exactly how or where it's invoked (wrapping the whole `config()` call in `{% if %}`, computing the value via a `{% set %}` block first, moving it earlier/later in the file — all tried, all failed the same way).
- **Decision**: Replace the pre_hook (which inherently needs `is_incremental()` to decide "should this even run") with a **post_hook that is purely self-referential and unconditional** — it operates only on the target table itself (closing out any `_is_current = true` row that now has a strictly newer row for the same key, immediately after this run's INSERT has landed), needs no incremental/first-run branching at all (correct, cheap no-op on a first build), and therefore has nothing adapter/manifest-dependent to feed into `config()`. Also had to switch from `UPDATE ... WHERE EXISTS (SELECT ... FROM <same table>)` to `MERGE INTO` — Delta rejects a self-referential correlated subquery in `UPDATE` (`[DELTA_UNSUPPORTED_SUBQUERY]`) but fully supports the equivalent `MERGE`. And the macro's `schema`/`table_name`/`business_key_col` arguments had to become plain hardcoded string literals per call site (not `this`/`model.meta`-derived) — the one place in this project's macros where DRY loses to "must survive the stub pass." Full writeup, with the three sequential sub-fixes attempted before landing on this design, lives in `dbt/macros/apply_scd2.sql`'s docstring ("Bug 3", parts 1–3).
- **Blast radius**: this redesign changes `apply_scd2.sql` and all three SCD2 models (`silver_contoso__customers.sql` from `001`, plus this spec's `silver_contoso__product.sql`/`silver_contoso__store.sql`) — `001`'s customers entity was re-validated (full rebuild + a fresh live delta) after the change to confirm no regression, even though its own historical delta-load test (T022) had, by luck of timing/positioning, not hit this particular failure mode.
- **Alternatives considered**: Trying yet another variation of computing the pre_hook value differently (e.g. a project-level `on-run-start` hook, or a separate `run-operation` invoked manually before each incremental build) — rejected; a manual extra step per build is worse ergonomics than a macro that's simply correct, and the post_hook redesign has no such cost once written.
